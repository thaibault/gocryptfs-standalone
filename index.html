gocryptfs-standalone

Synchronizes a gocryptfs (plaintext names) encrypted directory with a decrypted copy without needing FUSE or admin rights.

src.zip app.zip en de fr

Project status

Use case

Work with a gocryptfs encrypted folder (for example synchronized via a cloud service like Google Drive) on machines where gocryptfs or FUSE can not be installed, e.g. without admin rights. The tool runs as a single executable on Linux, macOS and Windows and keeps a decrypted copy in sync with the vault, also in the background.

Only vaults created with gocryptfs -init -plaintextnames are supported (feature flags "HKDF", "GCMIV128" and "PlaintextNames"). Every other vault is refused so it never gets damaged.

Installation

Download the executable of your platform from the releases ("linux", "macos" or "windows", each for "x64" and "arm64"), unpack it and run it, no installation or admin rights needed. "SHA256SUMS" lists the checksums of all archives. The executables are not signed by a registered developer:

  • macOS blocks them at first: remove the quarantine flag with xattr -d com.apple.quarantine gocryptfs-standalone-macos-* or allow it under "System Settings → Privacy & Security".
  • Windows SmartScreen may warn on first start ("More info → Run anyway").
  • Linux executables need a glibc based distribution (not Alpine or musl).

With Node.js 26 or newer the package also runs directly via npx gocryptfs-standalone ….

On Arch Linux the included "PKGBUILD" builds a package via "makepkg --install", installing "gocryptfs-standalone" into "/usr/bin".

Usage

gocryptfs-standalone init <vault> [--scryptn 16]
gocryptfs-standalone info <vault>
gocryptfs-standalone cat <vault> <path> > file
gocryptfs-standalone decrypt <vault> <target>
gocryptfs-standalone encrypt <source> <vault>
gocryptfs-standalone sync <plaintext> <vault> [--dry-run] [--trash-days 30]

"decrypt" and "encrypt" work one way: existing files on the target side get overwritten, nothing gets deleted. Modification times, permissions and symbolic links are carried over. Vaults created with "init" can be mounted with gocryptfs. "--help" lists all options.

The vault's configuration file is looked up as "gocryptfs.conf" and then as ".gocryptfs.conf" in the vault folder. "--config <path>" uses one located elsewhere, like gocryptfs' "-config" option, e.g. to keep it out of the cloud. Both names are reserved in the vault root and never synchronized.

Password of single commands

The password is taken from the first available source:

  1. "--passfile <path>": First line of the file.
  2. "--extpass <command>": First line of the command's output.
  3. Environment variable "GOCRYPTFS_PASSWORD".
  4. Interactive prompt.

"--masterkey <hex>" unlocks the vault with its master key instead. A given master key is checked against existing vault content before anything gets encrypted with it.

Synchronization

"sync" keeps a plaintext folder and a vault in sync in both directions. After each run the state of both sides is remembered in the user's configuration folder ("%APPDATA%\gocryptfs-standalone" on Windows, "$XDG_CONFIG_HOME/gocryptfs-standalone" or "~/.config/gocryptfs-standalone" elsewhere). Compared to that state:

  • Changed or new in the plaintext folder: encrypted into the vault.
  • Changed or new in the vault: decrypted into the plaintext folder.
  • Deleted on one side and unchanged on the other: the other version is moved into the trash.
  • Deleted on one side and changed on the other: the change wins and is copied again.
  • Changed on both sides: the newer version wins, the older one is kept as "name (conflict <host> <date>).ext" on both sides.

Without a state (first run) both sides get merged, files existing on both sides are compared by content, and nothing gets deleted. The trash lives next to the state ("pairs/<id>/trash", vault files stay encrypted there) and gets purged after 30 days ("--trash-days"). Entries changing while being synchronized are skipped and retried next time, a lock prevents parallel runs of the same pair. "--dry-run" only shows what would happen.

Excludes

"decrypt", "encrypt" and "sync" accept "--exclude <pattern>" (repeatable). Excluded entries are left alone on both sides as if they did not exist, excluding something already synchronized never deletes it. Patterns follow gitignore conventions:

  • ".DS_Store", ".tmp", "~$": Names at any depth.
  • "docs/.pdf", "docs/**/.pdf": Paths relative to the root.
  • "/build": Only in the root.
  • "cache/", "node_modules/": Only folders, with all their content.

Supported globs are "*", "**", "?", "[...]" and "{a,b}". Matching is case insensitive on macOS and Windows.

Configured pairs and background synchronization

Pairs of a plaintext folder and a vault can be configured once and then be synchronized by name, all at once or in the background:

# Asks for the password, verifies it and stores it in the keychain.
gocryptfs-standalone pair add documents ~/Documents/private ~/GoogleDrive/vault --interval 10m
gocryptfs-standalone pair list
gocryptfs-standalone sync documents        # one pair
gocryptfs-standalone sync                  # all pairs
gocryptfs-standalone daemon                # all pairs on changes and in their intervals
gocryptfs-standalone service install       # start "daemon" after each log in
gocryptfs-standalone service status
gocryptfs-standalone service uninstall
gocryptfs-standalone pair remove documents

Everything lives in "configuration.json" inside the configuration folder and can be edited by hand as well:

{
    "defaults": {
        "excludes": [".DS_Store", "._*", ".~lock.*#", "Thumbs.db", "desktop.ini", "~$*"],
        "interval": "10m",
        "trashDays": 30,
        "watch": true
    },
    "pairs": {
        "documents": {
            "plaintext": "/home/me/Documents/private",
            "vault": "/home/me/GoogleDrive/vault",
            "interval": "5m",
            "excludes": ["*.tmp", "build/"],
            "trashDays": 7,
            "watch": false,
            "password": "keychain",
            "config": "/home/me/vault.conf"
        }
    }
}

A pair's excludes are added to the default ones. "config" is only needed for a configuration file outside of the vault ("pair add --config"). Intervals take seconds, minutes or hours ("30s", "10m", "2h", at least 10 seconds). Pairs must not overlap: a folder of one pair must not be located inside one of another pair. Password sources:

  • "keychain" (default of "pair add"): The operating system's credential store, see below.
  • "prompt": Asked interactively, once when the daemon starts.
  • "environment": Environment variable "GOCRYPTFS_PASSWORD".
  • {"file": "<path>"}: First line of the file ("pair add --passfile").
  • {"command": "<command line>"}: First line of the output ("pair add --extpass").

Credential stores are used without native modules or admin rights:

  • macOS: Login keychain via "security".
  • Linux: Secret Service (GNOME Keyring, KWallet, …) via "secret-tool" (package "libsecret-tools" or similar).
  • Windows: DPAPI via PowerShell. The encrypted password is stored in "credentials/<pair>.dpapi" inside the configuration folder and can only be decrypted by the same user on the same machine.

Daemon

The daemon unlocks all vaults on start, so wrong passwords fail early, then synchronizes every pair right away and afterwards in its interval. Runs never overlap, failures get retried in the next interval, a run blocked by a parallel "sync" of the same pair after 10 seconds. Only one daemon watches a pair at a time, another one stops right away (exit code 4).

With "watch": true (default) the daemon additionally listens to file system events of both sides and synchronizes a pair 2 seconds after the last change, at the latest 30 seconds after the first one while changes keep coming. The interval stays as fallback, since cloud clients and network or FUSE mounts often do not report everything. If watching fails (e.g. Linux' inotify limit "fs.inotify.max_user_watches" is reached) the pair is synchronized in its interval only and watching is retried every 5 minutes. "--no-watch" disables watching for "pair add" or a single "daemon" run.

"service install" registers the daemon per user, without admin rights:

  • macOS: launchd agent "~/Library/LaunchAgents/com.tsickert.gocryptfs-standalone.plist", logging to "daemon.log" in the configuration folder.
  • Linux: systemd user unit "~/.config/systemd/user/gocryptfs-standalone.service" (log via journalctl --user -u gocryptfs-standalone, keep it running while logged out with loginctl enable-linger).
  • Windows: Command file in the user's startup folder, starting the daemon minimized and logging to "daemon.log" in the configuration folder.
